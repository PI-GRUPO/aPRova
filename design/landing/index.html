Nenhum PR de IA chega à main sem prova

PR é o pedido para juntar uma mudança ao código principal. main é a versão oficial do código.

Quando uma IA escreve código, alguém precisa conferir antes de ele entrar. O aPRova testa o código num ambiente isolado, sem internet, decide o risco com regras fixas e assina cada decisão. Se o risco for alto, o código espera uma pessoa aprovar.

  1. Uma IA propõe uma mudança

    Um agente de IA abre um pedido de mudança (PR) no GitHub, o site onde o código do projeto fica guardado. O GitHub avisa o aPRova na hora, e o aPRova abre uma análise para aquela versão exata do código.

    Webhook do GitHub App · uma análise por commit

    No PR #6A mudança foi feita numa cópia de trabalho (teste-peso-zero) e pede para entrar na main.

  2. O código roda isolado, sem internet

    Primeiro o aPRova baixa o que o código precisa. Depois roda os testes numa caixa fechada: sem internet e com um usuário sem poderes especiais. Se o código tentar acessar a internet, não consegue.

    Sandbox em duas etapas: preparar com rede, testar com --network none · usuário sem privilégio · Go, Python e Java

    No PR #610 testes passaram e 1 falhou.

  3. Regras fixas decidem o risco

    Sete regras olham o que mudou. A mesma mudança sempre dá o mesmo resultado. Nenhuma IA participa dessa decisão. Se nenhuma regra dispara, o risco é baixo.

    As sete regras e o risco que cada uma dá

    No PR #6«Os testes falharam» disparou. Risco alto.

  4. O histórico pode baixar um degrau

    Se casos muito parecidos já foram aprovados por pessoas e entraram sem problema, o aPRova pode baixar o risco um nível. Ele nunca sobe o risco e nunca baixa dois níveis. Teste falhando, biblioteca nova, senha no código e mudança na automação nunca baixam. Quando o nível cai, o motivo fica escrito no recibo.

    Calibração por histórico · desligada por padrão

    No PR #6Não se aplica: teste falhando nunca baixa.

  5. Cada decisão vira um recibo assinado

    O recibo é o registro assinado de cada decisão, que qualquer pessoa pode conferir. Ele guarda a versão exata do código, o resultado dos testes, o risco e os motivos. Cada recibo aponta para o anterior, como elos de uma corrente.

    Prova que foi essa a decisão, com esses dados, e que ninguém a mudou depois.

    Não prova que a decisão estava certa. Também não protege contra quem tiver a chave secreta que assina.

    Assinatura Ed25519 · recibo encadeado ao anterior

  6. O GitHub trava o botão de juntar

    O aPRova publica uma verificação que o GitHub exige antes de juntar o código. Enquanto ela não libera, o botão fica travado. Ele também deixa um único comentário no pedido e o atualiza a cada versão nova, sem encher a conversa.

    Check Run aPRova obrigatório na proteção da branch · um comentário por PR

    No PR #6Nem um administrador consegue pular a trava.

  7. Risco alto espera uma pessoa

    Quem tem permissão aprova pelo Slack, o chat da equipe, com uma justificativa. Se o Slack não responder, dá para aprovar pelo próprio GitHub. A aprovação vale só para a versão analisada: se o código mudar, a análise recomeça.

    Aprovação gravada com o commit analisado e a origem (Slack ou GitHub)

    No PR #6Na apresentação, a aprovação é feita pelo Slack.

  8. Se algo passou, o recibo ajuda a desfazer

    A partir do recibo, o aPRova encontra a mudança que entrou e prepara o comando e o texto para desfazê-la. Ele não executa nada: quem desfaz é uma pessoa, com a própria conta. Para isso, o aPRova só lê o código e não precisa de permissão para alterá-lo.

    Reversão assistida · GET /receipts/{id}/revert · só leitura

Também faz

Recursos de apoio. Nenhum deles muda a decisão de risco, e alguns ficam desligados até alguém ligar.

  • Mostra os motivos na aba de segurança do GitHub

    Os motivos do risco aparecem também como alertas no próprio pedido. Desligado por padrão.

    SARIF no code scanning

  • Diz como está funcionando

    Registra cada passo e mostra, para quem cuida do sistema, números de uso e se ele está no ar. Esses dados ficam num endereço interno, desligado até ser configurado.

    /metrics, /health/live e /health/ready

  • Tem limites de uso

    Cada conta que instala o aPRova inicia até 60 análises por hora; acima disso, o pedido espera na fila e continua barrado. Cada endereço de internet lê até 60 recibos por minuto. Nenhum limite libera código sem análise.

    Teto por instalação e por IP

  • Explica o risco em linguagem simples

    Se ligada, uma IA escreve um parágrafo no comentário explicando a decisão. Ela só descreve o que as regras já decidiram. Desligada por padrão.

    Explicação por IA (Gemini)

Qualquer pessoa pode confirmar que a decisão não foi alterada

Basta a chave pública do aPRova, que pode ser divulgada. Não precisa de conta, nem de acesso ao servidor, nem confiar em nós. A verificação roda no seu computador.

O recibo é assinado e verificável: o conteúdo é público, e a assinatura mostra se alguém mudou um único caractere.

Ver como conferir

Baixe o recibo do PR #6 e rode, com OpenSSL 3:

$ jq -r .payload_base64    recibo.json | openssl base64 -d -A > payload.bin
$ jq -r .assinatura_base64 recibo.json | openssl base64 -d -A > assinatura.bin
$ CHAVE='Jlx6KQYEoJTm/atXMaj53IJHUfJxKEDtKrtqPWKsm1s='
$ { printf '302a300506032b6570032100' | xxd -r -p; printf '%s' "$CHAVE" | openssl base64 -d -A; } \
    | openssl pkey -pubin -inform DER -out chave-publica.pem
$ openssl pkeyutl -verify -pubin -inkey chave-publica.pem -rawin -in payload.bin -sigfile assinatura.bin
Signature Verified Successfully

No macOS, o openssl que vem no sistema não confere Ed25519. Use o OpenSSL 3 do Homebrew (brew install openssl@3). A chave acima é a da instância usada na demonstração. Com um byte do recibo alterado, a resposta vira Signature Verification Failure.

Passo a passo completo

O aPRova barra o código quebrado e deixa passar o certo?

Pedimos a uma IA que resolvesse 21 exercícios de programação e mandamos cada solução ao aPRova. Um avaliador separado, com os testes originais de cada exercício, dizia quais soluções estavam certas. A tabela compara as duas coisas.

Rodada 1: a IA podia rodar os testes antes de entregar (claude-sonnet-5). Rodada 2b: a IA não podia rodar nada (claude-haiku-4-5).

Na rodada 2b, as 4 soluções quebradas foram barradas como risco alto, e nenhuma solução certa foi barrada. Em outros 6 casos montados de propósito, um para cada regra além dos testes falhando, 6 de 6 receberam o nível e o motivo esperados.

Limites: cada tarefa rodou uma vez; só 4 soluções quebradas; a rodada 2b trocou o modelo e tirou a execução ao mesmo tempo; a regra de código sem teste se engana com arquivos que só têm nome de teste. Relatório completo

O que o aPRova nunca faz

Isso vale sempre, em qualquer configuração.

  • Juntar o código sozinho

    Quem trava é o GitHub. Quem junta é uma pessoa.

  • Decidir o risco com IA

    Regras fixas decidem. A IA, quando ligada, só explica.

  • Liberar risco alto sem uma pessoa

    O pedido fica barrado até alguém com permissão aprovar.
